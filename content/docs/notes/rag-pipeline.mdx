先说结论：**RAG 的效果不是"换个更强的模型"换出来的，而是四侧各司其职拼出来的。** 索引侧决定上限，检索侧决定能不能命中，评测侧决定能不能持续迭代，消费侧决定最终答案可不可信。任何一侧偷懒，最后都会表现为"模型胡说"。

一句话记法：**索引定天花板，检索抢命中，评测守底线，消费管可信。**

## 一、全景

```text
wikidb/wiki/*.md
  → 解析 / 切块
  → Manifest（稳定 ID + 版本 + ACL）
  → PostgreSQL 状态库
  → Elasticsearch（倒排）+ Qdrant（向量）

query
  → 路由（hybrid / keyword / vector）
  → 召回（ES BM25 ∥ Qdrant 向量）
  → 过滤（ACL / 工艺域 / 异常类型）
  → 融合（RRF）
  → 重排（可选 rerank）
  → 出参（top-k 证据）
  → 消费（Agent 证据包 → LLM → 界面标注来源）
        ↑                    ↓
      评测侧（回归集 + 指标 + 基线门禁）
```

四个侧的边界要清晰，否则排障时会互相甩锅：

| 侧 | 时机 | 核心问题 | 出问题时的症状 |
| --- | --- | --- | --- |
| 索引侧 | 离线 | 知识有没有被正确切出来、写进去 | 怎么问都查不到、条数对不上 |
| 检索侧 | 在线 | 正确的那块有没有进 top-k、排第几 | 查到了但排得靠后、首条答非所问 |
| 评测侧 | 离线 | 改动到底是变好还是变坏 | 每次调参靠感觉、回归无人发现 |
| 消费侧 | 在线 | 证据有没有被正确使用和标注 | 答案没依据、把模型补写当原文 |

## 二、索引侧：上限在这里被决定

### 2.1 处理流程

| 步骤 | 做什么 | 关键点 |
| --- | --- | --- |
| 解析 | Markdown 按标题层级拆小节 | 保留 `title` / `heading_path`，别拍平成纯文本 |
| 切块 | 一个小节一个块 | 块太大会稀释关键词，太小会丢上下文 |
| 清洗 | 丢弃「来源」小节 | 这类块只有文件名和引用，占过 21% 的索引量 |
| 合并 | 同级过短小节并入前一块 | 阈值 20 字、合并后上限 400 字 |
| 编号 | 稳定 ID + 文档版本 | 增量同步和双库对齐全靠它 |
| 向量化 | `heading_path + 正文` 一起送 embedding | 只送正文，模型分不清片段出处 |
| 写入 | ES 与 Qdrant 双写，状态库存元数据 | 先删旧块再写新块，保证幂等 |

### 2.2 切块的四条硬规则

1. **按标题层级切，不按固定字数切**。固定窗口会把"原因"和"处置步骤"切到两个块里，检索到了也没法回答。
2. **短小节合并时保留原标题**。早期尝试直接合并、丢掉被并小节的标题，结果 BM25 的 `title` / `heading_path` 权重全部失效，指标明显下降。
3. **「来源」类小节直接丢**。判断只认精确标题，避免误伤「旧系统参考基准」「临时参考值」这类业务内容。
4. **块文本和向量文本分开**。展示用原文；向量化时在正文前拼上 `标题 / 章节路径`，这是低成本、高收益的一步。

### 2.3 稳定 ID 与增量同步

```text
doc_version = hash(doc_id, source_hash, acl_hash, parser_version)
chunk_id    = hash(doc_id, doc_version, chunk_ref)
chunk_ref   = heading_path#section-N
```

这组哈希带来两个能力：

- **内容没变就不重写**：source hash 和 parser 版本都不变，文档直接跳过。
- **切块规则一变，版本自动变**：`parser_version` 从 v2 升到 v3，所有文档的 `doc_version` 都变，增量同步会自然重建，不需要手工清库。

注意 `chunk_id` 里带了 `doc_version`，所以**重建后旧 chunk_id 全部失效**。评测集里的 `relevant_chunk_ids`、LLM 判定的 qrels 都绑定了当时的 chunk_id，重建后必须重跑，不能直接复用。

### 2.4 双写一致性

写入顺序：

```text
按 doc 删除旧块（ES + Qdrant）
  → 批量 embedding
  → upsert ES
  → upsert Qdrant
  → PostgreSQL 记录文档与块
```

一致性检查要覆盖四件事，缺一不可：

| 检查项 | 为什么必须查 |
| --- | --- |
| 文档/块条数 | 两侧条数不一致，说明有一边写失败 |
| chunk_id 缺失 | 抽取失败或删除范围过宽 |
| content_hash 一致 | 内容写旧了、或切块版本没更新 |
| 抽样向量非零 | **全零向量也能通过 hash 校验，但检索会静默失效** |

真实踩过的坑：ES 已经按新版本写了 510 条，Qdrant 还停在 378 条，检索表面正常，实际有一半知识永远召不回来。另外 Windows Docker Desktop 下不要 bind mount Qdrant 存储目录，实测重启后向量全部归零。

### 2.5 元数据与 ACL

每个块除了正文，还要带两类字段：

- **范围过滤**：`process_areas`、`incident_types`、`device_ids`、`agent_scope`、`knowledge_type`。由 front-matter 标签确定性映射，不做语义猜测。
- **真实性字段**：`review_status`、`content_origin`、`source_ref`。入库状态的 `approved` 只代表"通过入库契约"，不代表人工核验过；真正的可信度必须看这两个字段。

ACL 是"知识可见性"，不是登录鉴权。它只决定某块能不能进入候选集，用户身份和接口鉴权仍归上层业务。

## 三、检索侧：六层，每层只做一件事

| 层 | 职责 | 关键配置 / 做法 |
| --- | --- | --- |
| 1 路由 | 选单路还是混合、失败怎么降级 | `hybrid` 默认；`keyword` / `vector` 仅调试 |
| 2 召回 | 两路各取候选 | 每路 80 条，两路 topK 必须一致 |
| 3 过滤 | ACL 与结构化字段 | 查询期下推，不在 Python 里二次筛 |
| 4 融合 | RRF 合并排名 | `k=60`，两路权重各 1.0 |
| 5 重排 | 交叉编码器精排 | 可选，默认关闭；只处理 topN |
| 6 出参 | 截断与证据组装 | 最终 top-10 |

### 3.1 路由：状态要显式，不要用空列表混淆

返回状态比返回结果更重要：

| 状态 | 含义 | 上层动作 |
| --- | --- | --- |
| `hybrid` | 双路成功并完成融合 | 正常生成 |
| `degraded_bm25_only` | 向量路失败，只剩 BM25 | 可生成，但标注降级 |
| `degraded_vector_only` | 词法路失败，只剩向量 | 同上 |
| `no_results` | 链路正常但没命中 | 回答"知识库无依据" |
| `failed` | 两路都失败 | **终止分析，不生成处置建议** |

最后一条是安全边界：检索挂了还让模型自由发挥，比报错危险得多。

### 3.2 召回：两路的性格完全不同

**BM25 字段权重**（当前值）：

```text
title^1.5  heading_path^2  identifiers^3  source_locator^2  content  normalized_content
```

- `identifiers^3` 是专门为设备号、参数名、标准号准备的，精确字符串靠它兜底。
- `content` 不设权重，避免长正文把标题和编号挤掉。
- 同义词、业务词典放在分词器里，不要每次查询时拼。

**向量路**：1024 维、Cosine、查询向量与入库向量必须同一模型同一维度。全零向量要在写入前直接拒绝。

### 3.3 过滤：软加权优先于硬过滤

工艺域和异常类型只做**加权偏好**，不做硬过滤：

- ES：`bool.should` 加 `process_areas` boost 6、`incident_types` boost 3，未命中的文档仍参与排序。
- Qdrant：没有 `should boost`，先按 `top_k * 2` 放大候选，再按域命中 ×1.10、异常命中 ×1.05 重排。

原因很直接：索引里只有 39% 的块有工艺域、15% 有异常类型，硬过滤会把大部分未打标文档直接排除。保留一个 `hard` 模式只用于评测对照，验证"软加权确实更好"。

### 3.4 融合：RRF 的三个细节

```text
score(d) = Σ weight_i / (k + rank_i(d))     # k=60
```

1. **去重要做两次**：先按 `chunk_id` 合并两路重复项，再按 `content_hash` 去掉内容相同的块（同一段话被切进不同小节很常见）。
2. **单文档限流**：同一文档最多 3 块。不加这层，一篇通用文档能靠关键词密度占满 top-10。
3. **噪声块在融合前剔除**：索引页（导航块）和「来源」块默认不参与，除非查询本身是导航类。

### 3.5 重排：默认关闭，开启要守住三条

- **送审文本要带出处**：`文档：X / 章节：Y / 内容：Z`。切块中位数只有几十字，只给正文，模型分不清"安全原则"和"处置流程"。
- **导航类查询跳过重排**：目录页对导航查询是正确答案，但重排模型通常判它低相关。
- **固定保留原排序前 3**：实测纯重排会把原本第一的文档挪到后面，MRR 掉到 0.97 以下；保留前 3 名既拿召回收益又守住 top-1。

### 3.6 出参：证据包要能追溯

每个结果至少带：`rank`、`score`、`text`、`source`、`source_locator`、`section_path`、`retrieval_sources`（命中哪几路）、`review_status`、`content_origin`。少了后三个，前端就没法标注"这条是模型补写的、未核验"。

## 四、评测侧：把"感觉变好了"变成"数字变好了"

### 4.1 指标口径

| 指标 | 口径 | 坑 |
| --- | --- | --- |
| Recall@K | 命中相关文档 / 全部标注相关 | 标注只有文档级，块级召回会偏高 |
| MRR | 第一个相关结果的倒数排名 | 只反映首条质量 |
| nDCG@K | 按文档去重后计算 | 不去重会算出 nDCG>1 |
| Precision@K | 命中块数 / 实际返回数 | 未标注一律按 0，只能当下界 |
| HitRate | 是否至少命中一条 | 对"有没有"敏感，对"排第几"不敏感 |
| duplicate_rate | 结果内重复内容占比 | 融合和切块问题的早期信号 |
| doc_concentration | 单文档最大占比 | 高于 0.5 说明限流没生效 |

### 4.2 基线门禁

回归集跑完和 `baseline.json` 比，容差 0.02，任何受门禁指标低于"基线 − 0.02"就退出码 1：

```text
recall_at_k, precision_at_k, hit_rate, mrr, ndcg_at_k
```

两个细节：

- **case_count 必须一致**，否则直接失败。评测集悄悄少了几条，指标再好看也没意义。
- **qrels 指标不进门禁**。LLM 判定依赖当次 pooling 的 top-k，chunk 一变就不可复现，只用于横向参考。

### 4.3 一次完整的基线（100 条）

| 模式 | Recall@10 | MRR | nDCG@10 | 重复率 | 文档集中度 | 平均延迟 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| keyword | 0.8767 | 0.8862 | 0.8197 | 0.005 | 0.292 | 15 ms |
| vector | 0.9317 | 0.9560 | 0.9062 | 0.026 | 0.289 | 253 ms |
| hybrid | **0.9392** | **0.9825** | **0.9196** | **0.000** | 0.290 | 456 ms |

结论很清楚：hybrid 在召回、排序、重复率上全面占优，代价是延迟。向量路单独用已经不错，但重复率高，说明同文档多块问题更严重。

### 4.4 qrels 的正确用法

LLM 对每条用例的 top-k 逐块打 0/1/2 分，产出 `chunkId → label`：

- 用途：算可信的 precision、MAP，补上"未标注 ≠ 不相关"的缺口。
- 边界：pooling 只覆盖 top-k，**算不出 recall**，召回仍以回归集标注为准。
- 绑定：qrels 记录生成时的检索模式，模式不一致直接跳过，避免把"没判定过"当成 0。

## 五、消费侧：证据怎么进模型

一次分析不是只查一次：

1. **主查询**：拼上 `incident_type`、`phase`、`agent_id`、遥测字段名和领域术语，取 3 倍候选。
2. **阶段查询**：只拼 `phase` 和该阶段的术语，取 2 条，补"监管总管 / 专项 Agent / 安全沙箱"各自的职责边界。
3. **合并去重**：按 `source_locator` 去重，截到 5 条证据。

两条纪律：

- **检索失败就终止**。两路都挂时抛 `RagRetrievalFailed`，整条分析链停止，不生成"看起来合理"的处置建议。
- **真实性随证据走**。`review_status`、`content_origin` 一路传到提示词和界面，模型补写的内容必须显式标注，不能当项目原文引用。

## 六、排障顺序：从症状定位到侧

| 症状 | 先查什么 | 常见根因 |
| --- | --- | --- |
| 怎么问都查不到 | 索引侧 | 索引条数不对、全零向量、分词器/映射不一致 |
| 查到了但首条不对 | 检索侧 | 字段权重过高、融合偏一路、重排把首条挪走 |
| 指标整体下降 | 评测侧 | 评测集变了、chunk_id 失效、基线口径变了 |
| 召回够但答案没依据 | 消费侧 | 证据没注入、截断太短、提示词没约束引用 |
| 同一问题结果飘 | 索引/融合 | 双库不同步、重复块、单文档未限流 |

## 七、值得抄走的几个决定

1. **切块阶段就消灭噪声**：来源块、导航块不进索引，比在检索时过滤便宜得多。
2. **过滤条件全部下推**：ES 用 `bool.filter`，Qdrant 用 payload filter，不要让 Python 捞回来再筛。
3. **软加权替代硬过滤**：标签覆盖率低时，硬过滤等于主动丢召回。
4. **重排保留头部**：不要迷信 rerank 的全局重排，top-3 钉住是性价比最高的折中。
5. **评测先定口径再调参**：precision 用下界、nDCG 去重、qrels 不进门禁，写清楚才不会被数字骗。
6. **把"检索失败"当成一等状态**：降级可回答要标注，完全失败要终止，绝不静默降级成自由发挥。

## 八、还能往哪改

- 索引侧：给切块加语义边界（标题 + 段落主题变化），减少"一个块跨两个话题"。
- 检索侧：按查询类型路由（定义题偏 BM25、诊断题偏向量），而不是全局一个 hybrid。
- 融合侧：从固定权重过渡到按查询置信度动态调权。
- 评测侧：补"答案级"指标（引用是否支撑结论），把检索质量和生成质量分开看。
- 消费侧：把证据覆盖率、引用命中率做成线上指标，而不是只在离线看召回。
