先给结论：**被淘汰的不是"检索"，而是"文档切片 → 存向量库 → 取 top-k → 塞进 prompt"这一条固定流水线。** 检索能力只是被拆开、吸收进了 Agent 和上下文工程里，所以"RAG 这个产品品类"的声音变小了。

一句话记法：**检索从一条管线，变成了一个工具。**

## 一、朴素 RAG 到底长什么样

```text
文档 → 切块 → 向量化 → 向量库 → 相似度 top-k → 拼进 prompt → LLM 回答
```

这条链路在 demo 阶段非常好用：三天能跑通，看起来什么都能答。但它的所有能力都压在"向量相似度"这一个假设上——**语义相近的块，就是回答问题需要的块**。这个假设在真实业务里经常不成立。

## 二、为什么它的声音变小了

### 2.1 长上下文 + prompt caching 吃掉了小语料场景

几十万 token 的文档集、一个中等规模的代码库，现在可以直接全量放进上下文，配合 prompt caching，成本能压到可接受。

这么做省掉了整条工程链路：不用切块、不用管召回、不用重排，还顺手消灭了"chunk 被切断导致语义丢失"这个顽疾。**语料足够小且稳定时，全量塞进去就是比检索更准。**

### 2.2 朴素 RAG 在正确率上撞墙

企业场景要的是 95% 以上可用，而向量 top-k 在下面这些题目上系统性失效：

| 问题类型 | 为什么 top-k 救不了 |
| --- | --- |
| 多跳推理 | 「A 的负责部门的规定」需要先查到 A，再查规定，一次检索拿不到 |
| 聚合统计 | 「一共几个厂、平均加药量多少」——答案不在任何一块里 |
| 表格与数值 | 相似度对数字几乎无感，阈值、单位、口径全对不上 |
| 跨文档对比 | 需要多份证据并排，top-k 只会给你最像的那几段 |
| 否定与排除 | 「除了 X 还有哪些」这类语义，embedding 表达不出来 |

更麻烦的是**错了不可解释**：召回不对，你不知道是切块问题、embedding 问题还是排序问题。demo 的 70% 和生产的 95% 之间，差的不是模型，是这一整层排障能力。

### 2.3 Agentic search：检索从管线变成工具

既然固定管线不灵，那就让模型自己决定。

给 Agent 挂上 `search`、`grep`、`sql`、`fetch` 这些工具，它可以自己判断：要不要搜、搜什么词、搜到了够不够、要不要换个说法再搜一次。**检索从"每次必走的一步"变成了"按需调用的能力"。**

这条路更准，因为多跳、聚合这类问题天然需要多轮试探；代价是延迟和 token 成本都上去了，而且依赖模型稳定的工具调用能力。

### 2.4 结构化数据被 NL2SQL 直接接管

指标、阈值、报表、实时状态这类问题，本质是查库，不是找文档。生成 SQL 去查，准确率比向量检索高一个数量级，还能天然支持聚合和时间范围。

判断标准很简单：**答案能在数据库里算出来，就不要拿文档去"猜"。**

### 2.5 商业叙事放大了"降温"

RAG 创业公司高度同质化，准确率又很难在售前证明，采购自然降温；叠加"RAG is dead"这种标题带来的传播效应，就形成了"没人用了"的观感。

但看技术栈会发现相反的事实：混合检索、rerank、查询改写，**已经变成了主流 Agent 框架的默认能力**。RAG 不是消失了，是从"要单独买的东西"变成了"框架自带的一层"。

## 三、现在真正在替代它的方案

| 方案 | 解决什么 | 什么时候选 | 代价 |
| --- | --- | --- | --- |
| 长上下文 / CAG | 小语料全量可见 | 语料稳定、QPS 高、可缓存 | 超长上下文注意力衰减；缓存失效后成本陡增 |
| Agentic retrieval | 多跳、开放探索 | 问题不可预测，需要多轮试探 | 延迟高、token 贵、依赖工具调用稳定性 |
| NL2SQL / text-to-API | 数字、聚合、实时数据 | 答案存在于结构化库中 | 依赖 schema 质量，复杂 join 仍需兜底 |
| GraphRAG / 知识图谱 | 实体关系、全局摘要 | 需要"整体讲了什么"而非"哪段最像" | 构图成本高，增量更新麻烦 |
| 微调 / 蒸馏 | 固定技能、输出风格、术语 | 任务形态稳定、无需新知识 | 记不住新事实，仍然要配检索 |
| Memory 系统 | 个性化、长周期 Agent | 跨会话的用户偏好与历史 | 和"知识库"是两回事，不能混用 |

这些方案不是互斥的替代关系。**它们回答的是不同的问题**：

- 长上下文和 CAG 回答"能不能全看见"
- 检索回答"该看哪一段"
- NL2SQL 回答"该算一下"
- 图谱回答"它们之间什么关系"
- 微调回答"该怎么表达"
- Memory 回答"之前发生过什么"

## 四、生产里的真实形态：不是选一个，是路由

成熟的系统里，入口是一层**查询路由**，而不是一条固定的检索链：

```text
query
  → 意图判断
      ├─ 数值 / 聚合 / 实时 → NL2SQL / 业务 API
      ├─ 实体关系 / 全局问题 → 图谱或分层摘要
      ├─ 具体条款 / 工艺细节 → 混合检索（BM25 ∥ 向量 → 融合 → rerank）
      └─ 不确定 / 需要多步   → Agent 多轮检索，自己决定搜几次

  → 证据包（带来源、版本、位置）
  → LLM 生成（强制引用）
  → 后验校验（引用是否真的支持结论）
```

所以"替代 RAG"这个说法本身是错位的：**大多数团队最后落到的，是能够自己决定要不要检索的 Agentic RAG，而不是某个单一方案。**

## 五、落到自己的项目怎么选

我在做的是水厂水质治理的 AI 分析：参数超阈值触发归因、给处置方案、人工审批后闭环。这类场景有个硬约束——**错了要有人负责，所以每条结论都得能溯回原文**。

这恰恰是长上下文方案最弱的地方：它能答得漂亮，但你很难说清这句话来自哪份文件的哪一节。所以结论是：

1. **检索继续用**，但换成混合检索：BM25 抓工艺名词和编号，向量抓语义，RRF 融合后 rerank
2. **数值类问题分流**：阈值、加药量、超标次数走结构化查询，不进语义检索
3. **允许二次检索**：首轮召回不够时，让模型改写查询再搜一次，而不是硬答
4. **引用与校验不省**：证据包里带来源和版本，生成后回验引用是否支持结论

一句话：**别把"向量库 top-k"当成 RAG 的全部。** 那只是它最简陋的一个实现。

## 一句话记法

RAG 从来没有输给长上下文或 Agent——输的是"只靠语义相似度"这一种实现方式。**检索是能力，RAG 是其中一种过时的封装。**
