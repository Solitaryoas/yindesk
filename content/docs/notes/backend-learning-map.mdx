## 前言&水平定位

**阅读本文的人，请自己先检查自己的Level，根据Level选择性的阅读下文：**

- L1：无任何语言等基础。
- L2：具备一定语言基础，无后端基础（接口、Mysql、HTTP请求等）。
- L3：具备后端、Mysql，框架等基础，能写出最简单的增删改查基础。（前端同学走全栈也应该到这里）
- L4：具备最简单的中间件能力，缓存（Redis），消息队列等。使用过Redis做缓存，消息队列发送消息。但不深入理解Redis、MQ等中间件的架构设计、设计思想、使用场景等。
- L5：具备后端最基础的能力，掌握数据库、接口通信、Redis、MQ，并且对于所学技术栈的架构与思想已经有一定的了解。但对于微服务、分布式架构，以及更深层的复杂业务没有理解。依旧停留在单体curd。
- L6：具备分布式能力，做过复杂的大型项目（至少3个以上不同的部门要对接），参与过复杂业务如：电商、广告、履约、交易、归因、外部多平台对接、ERP、定制化WorkFlow等。
- L7：能够独立阅读prd，出具技术方案，在某一单一领域能负责从需求拆解->技术方案设计->coding->验证闭环->持续迭代的能力。

### 不同语言的细分区别

- Golang更多会做基础设施、中间件等。如网关、缓存、RPC框架等。对性能的追求更高，语法也更简洁。当下大多数公司，无论是做业务还是搭基础设施（devops），只要有性能需求的，基本都会上Golang。如B站、抖音、腾讯（半Golang半C++）等。
- Java，互联网后端的半壁江山（过去是PHP），由阿里、电商、支付等把Java带到了一个新的高度。你现在用的app、网站里面，百分之七八十都是Java搭的后端。Java的生态更成熟，组件更多。最主要是用的公司多，所以并不是说Java多好用，多牛逼。本质上是技术历史的演变，中国互联网的发展，所以导致Java的岗位最多。Java并没有太突出的地方（除了生态），所以相对来说，Java一般用来写电商、物流、广告等业务。而字节、B站选Golang，因为Golang性能更高（支持短视频、直播、IM等更追求高性能的业务）
- node.js，轻量化。小公司会用，更多的时候搭配全栈，移动、出海等业务，以及外企公司用得最多。
- python，有更多跟llm相关的框架，以及数据、爬虫等。但其实无所谓，个人觉得可以跟Java放到一个定位。
- C++。除了鹅是以C++为主要后端语言。其他情况下，C++能做的方向：基础设施、中间件（同Golang）。上位机方向（制造业后端）。游戏服务端方向（C++最多的就业方向，要求也低，我没有游开基础，春招拿了15k的淘米游开后端offer）。

#### 先读后插（Select-then-Insert）并发问题详解

**1. 问题场景**

先读后插是一个典型的数据库并发问题：业务需要先查询某条记录是否存在，如果不存在则插入。在高并发场景下，多个请求可能同时读取到"不存在"的结果，导致重复插入。

**2. 并发问题演示**

**3. 问题根因分析**

**4. 解决方案对比**

| 方案 | 实现方式 | 优点 | 缺点 | 适用场景 |
|-|-|-|-|-|
| **唯一索引** | `UNIQUE KEY(username)` | 简单可靠，数据库层保证 | 需要处理异常 | ✅ 推荐首选 |
| **分布式锁** | Redis SETNX | 业务层控制，灵活 | 性能开销大，复杂度高 | 跨表、跨库场景 |
| **乐观锁** | 版本号/时间戳 | 无锁等待，高性能 | 需要重试机制 | 高并发读多写少 |
| **悲观锁** | SELECT FOR UPDATE | 强一致性保证 | 锁等待，性能差 | 强一致性要求 |
| **INSERT IGNORE** | MySQL 特性 | 写法简单 | 依赖唯一索引 | 可容忍静默失败 |
| **ON DUPLICATE KEY** | MySQL 特性 | 支持更新逻辑 | 语法较复杂 | 存在则更新场景 |

**5. 方案一：唯一索引（推荐）**

**代码示例（Java + MyBatis）：**

```java
// 1. 数据库建表
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_username (username)  -- 唯一索引
);

// 2. 业务代码
public class UserService {
    public Result<Long> register(String username, String email) {
        try {
            User user = new User();
            user.setUsername(username);
            user.setEmail(email);
            
            userMapper.insert(user);  // 直接插入
            
            return Result.success(user.getId());
            
        } catch (DuplicateKeyException e) {
            // 捕获唯一索引冲突异常
            return Result.fail("用户名已存在");
        }
    }
}

```

**6. 方案二：分布式锁**

**代码示例（Java + Redisson）：**

```java
public class UserService {
    @Autowired
    private RedissonClient redisson;
    
    public Result<Long> register(String username, String email) {
        String lockKey = "lock:user:" + username;
        RLock lock = redisson.getLock(lockKey);
        
        try {
            // 尝试加锁，最多等待5秒，锁超时10秒
            if (lock.tryLock(5, 10, TimeUnit.SECONDS)) {
                // 查询用户是否存在
                User exist = userMapper.selectByUsername(username);
                if (exist != null) {
                    return Result.fail("用户名已存在");
                }
                
                // 插入新用户
                User user = new User();
                user.setUsername(username);
                user.setEmail(email);
                userMapper.insert(user);
                
                return Result.success(user.getId());
            } else {
                return Result.fail("系统繁忙，请稍后重试");
            }
        } catch (InterruptedException e) {
            return Result.fail("操作被中断");
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();  // 释放锁
            }
        }
    }
}

```

**7. 方案三：悲观锁（SELECT FOR UPDATE）**

**代码示例（Java + MyBatis）：**

```java
// MyBatis Mapper
@Select("SELECT * FROM users WHERE username = #{username} FOR UPDATE")
User selectByUsernameForUpdate(String username);

// Service
@Transactional(isolation = Isolation.REPEATABLE_READ)
public Result<Long> register(String username, String email) {
    // 加悲观锁查询
    User exist = userMapper.selectByUsernameForUpdate(username);
    
    if (exist != null) {
        return Result.fail("用户名已存在");
    }
    
    User user = new User();
    user.setUsername(username);
    user.setEmail(email);
    userMapper.insert(user);
    
    return Result.success(user.getId());
}

```

**8. 方案四：INSERT IGNORE / ON DUPLICATE KEY UPDATE**

**代码示例（MySQL）：**

```sql
-- 方式1：INSERT IGNORE（静默失败）
INSERT IGNORE INTO users (username, email) 
VALUES ('alice', 'alice@example.com');

-- 方式2：ON DUPLICATE KEY UPDATE（存在则更新）
INSERT INTO users (username, email, created_at) 
VALUES ('alice', 'alice@example.com', NOW())
ON DUPLICATE KEY UPDATE 
    email = VALUES(email),
    updated_at = NOW();

-- 方式3：INSERT ... SELECT（先判断）
INSERT INTO users (username, email)
SELECT 'alice', 'alice@example.com'
FROM DUAL
WHERE NOT EXISTS (
    SELECT 1 FROM users WHERE username = 'alice'
);

```

**11. 常见陷阱与避坑指南**

**典型错误案例：**

```java
// ❌ 错误写法：无任何并发控制
public void register(String username) {
    User exist = userMapper.selectByUsername(username);
    if (exist == null) {  // 竞态条件窗口
        User user = new User();
        user.setUsername(username);
        userMapper.insert(user);  // 可能重复插入
    }
}

// ✅ 正确写法：依赖唯一索引
public void register(String username) {
    try {
        User user = new User();
        user.setUsername(username);
        userMapper.insert(user);
    } catch (DuplicateKeyException e) {
        throw new BusinessException("用户名已存在");
    }
}

```

  - 团队理解成本。
  - 中间件叠加成本。
  - 当前代码改造成本。

### Part 1 需求开发流程

我们先简单过一遍需求->开发->上线的流程

#### 发现需求

- 发现需求，这里一般是业务老板定方向、产品模式，然后交给下面的产品、运营团队执行。
- 比如老板说，我们这个季度要做社交、帖子的功能。产品、运营调研市场。运营负责制定未来功能上线后的打法，探查用户留存、转化。产品负责做老板、运营、开发之间的桥梁。梳理需求实现方式，平衡交付、技术、项目开发等成本。
- 产品梳理好需求后，通过figma编写prd的原型稿。
- 找到开发，开需求评审会。到处要资源，定开发周期。

#### 需求&技术评审

- 技术过完需求评审后。跟产品扯皮

  - 哪些能做哪些不能做。
  - 哪些做了花的时间比较久。（平衡项目交付和项目质量）
  - 给出对应的排期。
- 开发开始梳理技术方案

  - 技术方案选型。
  - 数据库。
  - 接口。
  - 排期。

    - 开发周期。
    - 联调周期。
    - 测试周期。
    - 验收时间。

#### 开发&联调&提测

- 理出需求排期后，开发开始设计技术方案。我们从后端的角度讲怎么理。
- 首先，你要注意这几件事：

  - 涉及到哪些数据库、表。
  - 要新增哪些接口。（基本上最重要的就是接口了 前端 测试 上来都先找的这个）
  - 后端服务之间有哪些上下游

    - 上游：流量入口，比如A服务a接口，被B服务调用，B就是上上游。
    - 下游：流量承接者。同样上面的例子，A就是B的下游。
  - 业务涉及到哪些链路。
  - 发布的时候要注意什么？比如A依赖B的新接口，就应该B先发，A后发。
- 写好技术方案的文档后，拉着同组的其他开发（前后端、安全、运维等）、测试，评估技术方案是否合理。
- 评估通过，开始开发。开发->自测（至少确保接口跑通）->联调->冒烟用例跑通（你至少要把所有的交互流程都走通，触发一遍）->提测->测试介入，执行test case。

#### 上线

- 我们就不讲简单的发布了（那种直接把新版本的代码部署到机器上的），我们来聊两个比较有含金量的：

  - 蓝绿发布（懒的自己写了 给豆包解释贴这里吧）：

    - 蓝绿发布是零停机全量上线部署方案，核心是维持两套配置完全一致的生产集群（蓝环境、绿环境）：
    - 蓝环境：承载正式流量，运行线上稳定旧版本
    - 绿环境：闲置备用，用来部署新版本、全量验证 通过负载均衡 / 网关一键切换全量流量完成上线；新版本故障直接切回旧集群，实现秒级回滚。

    ### 优点

    1. 真正零停机发布，用户无感知升级；
    2. 回滚成本极低，仅修改路由配置，秒级止损，是重大版本、核心业务首选；
    3. 新旧环境物理隔离，不会出现滚动发布的新旧实例共存、接口兼容错乱问题；
    4. 备用集群可直接用作容灾备份。

### Part 2 分布式数据一致性

OK，进入到网上垃圾八股最多的内容。

说到这块的内容，铺天盖地的：

- CAP
- BASE
- Seata
- 2PC
- TCC

并不是说这些东西、理论没有意义。这些东西对于自己长远提升很有意义。但问题在于这套理论基本没有太好的落地场景，国内百分之九十九的大厂业务也不会用这套东西。

点名某字母培训班，天天扯那个B Seata。纯粹的没上过班。

我先直接讲结论：

**大厂至少百分之九十九的业务，用的都是最终一致性，傻逼才用强一致。**

2PC、TCC 全程锁住资源，库存、订单、支付链路并发直接打不动，电商大促、直播下单完全扛不住。要么服务线程池打满，要么数据库连接池打满。轻则阻塞所有请求，重则直接打崩机器。

那怎么办？扩机器么？机器可比人贵多了，运维成本、机房维护成本，折旧成本。

所以我们选择最终一致性，是技术成本，机器成本，实现成本，吞吐性各方因素下最终做的妥协。ROI最高的方案。

只要我们保证一件事：**数据账一定要对得上！！**

**绝对红线：最终落账必须持平，订单总额 = 支付总额 - 退款总额，出库数量 = 订单发货数量。**

总之你记住一句话，大多数业务都有一定时间窗口的容忍度，不需要强一致，只要数据可追溯，有凭据。最终的数据账对得上就行。定时任务、消息重试。最终在数据维度、业务维度一致即可。

放了这么多屁，我们直接来一个实战场景看看吧：

#### 数据最终一致性 实战

我们简单想像一个场景，你在开发一个小区物业系统，这个物业系统涵盖了缴费、水电记录查询、单元管理等等功能。

由于有缴费功能，所以我们需要对接三方的支付SDK，这里就拿微信支付举例。

支付流程：前端点击支付->传给后端订单号（在前置订单生成接口就已经生成）、openID（微信同一小程序/公众号纬度下，用户的唯一标识）->后端调用微信支付API,入参：notify_url(回调地址，这个很核心，会单独讲),支付金额、微信交易号、商户号等->微信支付完毕->回调notify_url->后端感知到支付完成->更新订单状态（支付完成）->发放对应的权益（比如发放电费额度、水费额度等）。

##### 最核心的地方 回调

我们先来理解回调这个概念是做什么的。

**同步调用接口**

先说我们平时的接口，假如一条接口把整条业务全做了，比如从订单号生成->支付->权益发放。我们没有做流程、产品适用维度的拆分，就是一个接口全做了。

用银行取钱来比喻：

场景1：简单的取钱

1. 你把银行卡、取钱申请递给柜员
2. 柜员全程当场处理：核验余额、扣款、给现金
3. 整个过程你站在窗口不能走，处理完立刻拿到钱走人

场景2：大额取现需要审批，柜员没法当场给你钱。

你总不可能一直在柜台等着吧，等着人家找行长，找老板，走复杂的审批，评估。你这条线程不能一直卡在这个流程上吧。

1. 提交取钱申请，银行收下单据，给你一张回执单（prepay_id），让你先回家等着
2. 银行内部审批、出款完成之后，主动给你预留手机号打电话（调用你的 notify_url 接口），告诉你钱已经处理好了
3. 你接到电话，登记确认，完成后续操作

**对应微信支付逻辑**

1. 后端下单拿到支付凭证，用户去微信付款
2. 微信扣款完成，主动请求你的回调接口通知结果
3. 你接收通知更新订单、发放权益

这种方式，本质上是将同步调用，阻塞等待的重任务，拆成了异步任务。

我不在那里傻等你处理完请求，我给你一个回调接口，你做完你手上的事调我的回调接口通知我，我再去做我手里的事（比如取了钱狠狠的去happy，这个节点必须依赖前置的取钱节点）。

假如说我们不用回调，我们接口就要一直等微信返回。或者我们不想等微信返回，我们要保持吞吐量，保留我们宝贵的线程资源。另一种方式就是调完接口就断开。然后开个新的轮询任务，隔三差五去查下微信的api，这笔支付有没有成功。这样太浪费性能、时间了。

这就是回调，一句话总结：**不用你持续主动轮询查询结果，业务方处理完成后主动推送结果，节省轮询带宽与服务压力。**

##### 那如果回调丢了呢？

回调丢了的话，微信那边是会重试的，但是是阶梯式重试。
