用 AI 写代码久了会发现：**提示词是不可复用的，流程才是。** 同一句"帮我实现这个功能"，每次得到的质量天差地别，因为缺的不是措辞，而是一套稳定的动作序列。

Skills 解决的正是这件事——把"怎么做"固化成一个个可被路由的能力单元。我目前装了 17 个，它们不是并列的工具，而是**一条从想法到合并的流水线**。

## 一、总调度：yin-ai-flow

整个库的入口是一个路由型 skill，它不做具体的事，只负责**按阶段挑技能**：

| 阶段 | 触发语 | 使用的 skill | 产出 |
| --- | --- | --- | --- |
| 0 仓库初始化 | setup skills | setup-matt-pocock-skills | issue tracker、triage 标签、领域文档目录 |
| 1 澄清 | grill 我、压测这个想法 | grilling / grill-with-docs | 被证伪或打磨后的方案 |
| 2 建模与规格 | 建模、写 spec、拆票 | domain-modeling → codebase-design → to-spec → to-tickets | GLOSSARY/ADR → 模块接缝 → spec → 带阻塞边的票 |
| 3 实现 | TDD 做这个 | tdd（主线）+ ponytail（约束） | 红绿重构 + 最小实现 |
| 4 评审 | review 这个分支 | code-review | Standards + Spec 双代理报告 |

关键在于"**每个阶段只加载该阶段需要的 skill**"。一次把 17 个技能全塞进上下文，不但浪费 token，还会让模型在错误阶段做正确的事——比如实现阶段跑去质疑需求。

## 二、按阶段拆开看

### 0. 初始化：setup-matt-pocock-skills

前面那些技能都假设仓库里有几个约定：issue 记在哪（GitHub / GitLab / 本地 markdown）、triage 标签词表、领域文档放哪。这个 skill 就是**一次性把这些约定谈定并写下来**，产出 `docs/agents/*.md`，并在 `AGENTS.md` 或 `CLAUDE.md` 里留一个 `## Agent skills` 块。

它的做法值得注意：**先探索、再汇报、最后逐节确认**（一节一问，每节先给推荐答案），而不是一口气问十个问题。

### 1. 澄清：grilling / grill-with-docs

`grilling` 把需求澄清形式化成一棵**设计树**：每个决策都会分叉出依赖它的子决策。每一轮只问"**前沿**"——所有前置条件都已确定、现在就能回答的问题。一轮 = 编号问题 + 每题的推荐答案，然后停下来等回答。

两条规则很硬：

- **找事实是 AI 的活，不是用户的活。** 需要读文件、查环境才能回答的问题，派子代理去找，绝不问用户。
- **决策是用户的。** 每个决策都摆到台面上等确认，不替用户拍板。

`grill-with-docs` 是它的变体：一边压测方案，一边**顺手把 ADR 和术语表写出来**。

### 2. 建模与规格：四个 skill 串成一条链

这一阶段最容易糊弄过去，也最值钱：

- **domain-modeling**：主动维护项目的领域模型。用户用词模糊时立刻追问（"你说的 account 是 Customer 还是 User？"），用术语表校验，用具体场景压测边界，并且**当场**更新 `GLOSSARY.md`。它有个克制的规矩：只有当决策同时满足"难以逆转 + 没有上下文会令人费解 + 是真实取舍的结果"三条时，才建议写 ADR。
- **codebase-design**：一套**共享词汇**——module / interface / depth / seam / adapter / leverage / locality。核心主张是"深模块"：小接口背后藏大量行为。两个判据特别实用：**删除测试**（删掉这个模块，复杂度是消失了还是散落到 N 个调用点？）和"**一个适配器是假接口，两个才是真接缝**"。
- **to-spec**：不访谈，直接把已有对话和代码库理解综合成 spec，扔进 issue tracker，打上 `ready-for-agent` 标签。
- **to-tickets**：把 spec 拆成 **tracer bullet 票**——每个票是切穿所有层的垂直切片，能独立验收，且**自带阻塞边**（谁必须先完成）。宽重构是例外，要拆成"扩张—迁移—收缩"三段。

### 3. 实现：tdd + ponytail

`tdd` 管的是"**测试值不值得留**"，而不是"先写测试"这么简单：

- 测试只写在**事先约定好的接缝**上，写在接口上而不是实现细节上；
- 三条反模式：实现耦合、**同义反复**（断言用代码的方式重算期望值，永远无法与代码分歧）、水平切片（先写完所有测试再写实现）；
- 明确声明：**重构不属于红绿循环**，它属于评审阶段。

`ponytail` 是全程生效的**约束**，逼你走"最懒但有效"的路径，有个七级阶梯：这需求需要存在吗 → 代码库里已有吗 → 标准库能做吗 → 平台原生能力能做吗 → 已装的依赖能解决吗 → 能一行吗 → 最后才写最小实现。它同时守住了底线：**信任边界的输入校验、防数据丢失的错误处理、安全、无障碍，永远不简化。**

### 4. 评审：code-review

两个**互相隔离的子代理并行**跑，产出两份报告，且**刻意不合并排名**：

- **Standards**：代码是否符合仓库文档化的标准？外加一份固定的 Fowler 坏味道基线（神秘命名、重复代码、依恋情结、数据泥团……），每个都只是"可能"的启发式判断，且仓库标准永远优先。
- **Spec**：代码是否忠实实现了最初的 spec？漏做了什么、多做了什么（范围蔓延）、看着做了但做错了什么。

分开的理由很直白：符合所有规范但实现错了东西，和精确实现需求但破坏了项目惯例，是**两种不同的失败**，合并排名会让一条轴掩盖另一条。

### 诊断：diagnosing-bugs

单独的一条路径，用户说"诊断/调优/变慢"时触发。它有一条不可绕过的铁律：

**先建立能变红的反馈回路，没有回路不得进入假设阶段。**

信号必须"红得起来"——能驱动真实代码路径、断言用户描述的**那个**症状，而不是"没报错"。然后才是复现与最小化、3–5 条可证伪假设、一次只改一个变量的插桩、修好并留回归测试、清理掉所有 `[DEBUG-xxxx]` 埋点。

## 三、前端支线

前端不进主线，与阶段 2–3 并行。路由规则是**只在需要时选一个**：

| 场景 | 用哪个 |
| --- | --- |
| 有 Figma 链接或 node id | figma（先取设计上下文与截图，再翻译成本项目约定） |
| 项目用 shadcn/ui 或存在 `components.json` | shadcn（查已有组件、用语义色、不手搓标记） |
| 落地页、作品集、重设计 | design-taste-frontend |
| 后台、组件、常规页面 | frontend-design |
| 需要强视觉原型或 demo | frontend-skill |

这三个视觉类 skill 的分工很有意思：`design-taste-frontend` 走的是**先读题再出手**——先输出一句"Design Read"（这是什么页面、给谁看、什么语气），再据此设定三个拨盘（版式变化度 / 动效强度 / 信息密度），还带一整套"AI 味"反模式清单（紫色的渐变、居中的 hero、三张等宽卡片、Inter + slate-900）。`frontend-skill` 则强调**克制**：先构图再组件，默认不用卡片，第一个视口当海报而不是文档。

## 四、横切规则与边界

两条贯穿全程的规则：

- **ponytail 全程适用**：能不加就不加，优先标准库。
- **domain-modeling 随时调用**：术语或决策一变，就回去维护术语表和 ADR。

边界同样重要——**这个流程不硬扛所有事**：

- 需要计划审批或跨组件规格时，交给产品内置的 Plan / Spec 模式；
- 需要浏览器验证走 `TRAE-browseruse`；
- 安全审计走 `TRAE-security-review`；
- 纯静态、一眼可见的问题**直接修**，不启动诊断流程。

## 五、提炼出来的几条原则

1. **每阶段只加载该阶段的技能**，上下文是稀缺资源。
2. **事实自己查，决策交给用户**——这是几乎所有 skill 反复强调的分工。
3. **先有信号，再有假设**：无论调试还是评审，都得先有一个能变红的判据。
4. **文档跟着讨论走**：术语一确定就写进 GLOSSARY，决策一落定就记 ADR，绝不批量补写。
5. **约束比能力更重要**：ponytail 这样的"减法 skill"和 tdd 这样的"验证 skill"，实际收益往往高于再多一个生成器。

<Callout type="info" title="一句话总结">
  Skills 的价值不在于让 AI 多做点什么，而在于让它在**正确的阶段、用正确的方式**少做点什么。
</Callout>
